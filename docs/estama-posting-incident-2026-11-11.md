# 艶華・魂セラピスト同時投稿障害 — 調査結果と再発防止レポート

作成日: 2026-11-11（JST）  
対象: キャスト写メ日記の HP → O2 → 魂セラピスト同時投稿、および同じ共通モジュールを利用するエステ魂定期更新

## 結論（原因確定）

**Vercelのサーバー実行時、`server/estama-automation.js` が `/var/task/src/lib/estamaProfileData.ts` を読み込もうとしたが、配布先にこのTypeScriptファイルが存在せず、`ERR_MODULE_NOT_FOUND` で関数が起動前に終了していた。**

Vercelの実行ログで、該当ファイル名を含む `ERR_MODULE_NOT_FOUND` を直接確認した。よって、原因は「伊藤れなの操作」「エステ魂が投稿を拒否」「Browserbase無料枠」「Vercelのドメイン認証」ではない。認証やエステ魂操作の前にプログラムが停止している。

### 直接原因

`server/estama-automation.ts` の共通処理が、本来フロントエンド用の `../src/lib/estamaProfileData.ts` を実行時読み込み先として参照していた。サーバーに必要なコードが同じ配布単位のJavaScriptとして確実に含まれていなかった。

### なぜ検知が遅れたか

ソースが存在すれば通る開発・ビルドと、Vercel本番で必要なファイルが揃っているかの確認は別。サーバー関数の**起動テスト**と定期監視が無かったため、関数が起動時に停止する状態を事前検知できなかった。加えてSupabase側では「送信結果不明」という安全側の共通エラーに置き換えられ、根本原因が画面から判別しづらかった。

## 確認された影響

- 2026-11-07 21:53頃（JST）: 伊藤れなの投稿が魂側のみ失敗扱い。
- 2026-11-08 15:34頃（JST）: 伊藤れなの投稿「まってるよ〜〜👙🩵」で同種エラー。HPとO2は成功。
- 2026-11-11 05:33頃（JST）: 魂だけに送った「【動作確認】」投稿が同種エラーで停止。HPとO2へは送信していない。
- 2026-11-11 16:09頃（JST）: 投稿ワーカーへの非投稿型GET検査でもHTTP 500、`FUNCTION_INVOCATION_FAILED`。Vercel実行ログで上記モジュール不足が明らかになった。
- 同じ共通モジュールを利用する `/api/cron/estama-appeal` でもVercelに同じ起動エラーが複数記録されていた。その他のエステ魂連携機能への波及可能性あり。

**注意:** 「魂セラピストに実際に1件も掲載されていない」ことは公開一覧との突き合わせを終えるまで断定できない。既存の投稿を自動再送しない制御は継続する。

## 修正

1. サーバー専用の `server/estama-profile-data.ts` を新設。既存の変換処理をサーバー配布可能なモジュールへ移し、依存先を `./estama-sns-links.js` として参照する。
2. `server/estama-automation.ts` がフロントエンドの `.ts` ファイルを直接読み込まないよう、`./estama-profile-data.js` に変更。
3. `tests/estamaProfileRuntime.test.ts` を追加。フロント側とサーバー側の変換内容一致、危険な読み込み参照の再混入、投稿ワーカーの非投稿型GETの動作を検証する。
4. `.github/workflows/estama-worker-health.yml` を追加。PR/本番ブランチ変更時にコード検査。毎時13分に本番URLへ**投稿を発生させないGET**を送り、正常なら405、起動失敗なら500として検出。失敗した場合GitHub Actionsを失敗にする。

## 検証基準

- GitHubの追加テストが成功。
- Vercelの本番デプロイがREADY。
- 本番の非投稿型GETで **HTTP 405** を確認（従来はHTTP 500）。
- Vercelログに `ERR_MODULE_NOT_FOUND` が再出現しない。
- 最終的な魂への投稿確認は、既存投稿との重複を確認したうえで新規テストを1件送信し、公開画面と写真枚数を照合する。

## 未完了時の取り扱い

本番の起動確認が通る前に、既存の「要確認・再送停止」投稿を一括再送しない。実際の掲載確認が必要な投稿は、11/7・11/8の2件と11/11のテスト1件。送信履歴を消して成功と見なすことは禁止。

## 運用上の再発防止

デプロイ直後と定期的な起動確認を必須にする。投稿失敗時は「外部の投稿拒否」「ログイン切れ」「サーバー関数が起動できない」「投稿済みだが確認できない」を区別して記録し、再送可否は投稿前後の確実な証拠で判定する。監視失敗時はGitHub Actionsの失敗履歴を確認し、`ERR_MODULE_NOT_FOUND` などのログに基づいて復旧する。
